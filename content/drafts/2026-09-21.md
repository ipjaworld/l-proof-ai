# L-Proof-AI 월요일 브리핑 초안

## 에이전트가 오래 일할수록, 사람의 승인선이 제품이 된다

이번 주의 공통점은 모델 성능보다 **에이전트가 얼마나 오래 일하고, 얼마나 많은 도구와 하위 에이전트를 조율하며, 어디에서 사람에게 결과를 돌려주는가**에 있습니다. OpenAI는 관리형 에이전트 실행 기반을 API로 내놓았고, Cursor는 수개월짜리 프로젝트와 반복 작업을 조율하는 제품을 공개했습니다. GitHub는 코드리뷰 에이전트가 셸 도구와 여러 에이전트를 이용해 검증 범위를 넓혔다고 밝혔습니다.

자동화의 단위가 “한 번의 답변”에서 “지속되는 업무”로 바뀌는 중입니다. 이때 경쟁력은 완전 자동화가 아니라, **어디에서 멈추고 사람이 판단하게 할지 설계하는 능력**에서 나옵니다.

## 1. OpenAI, 장기 실행 에이전트를 위한 Agents API 공개

**발표일** 2026-09-10
**검증 등급** 03 · 공식 확인
**직접 테스트** 아직 하지 않음

### 사실 요약

OpenAI가 Codex에 쓰이는 에이전트 하네스와 실행 인프라를 개발자가 사용할 수 있도록 Agents API를 공개 베타로 출시했습니다. 작업·모델·도구·환경을 지정해 에이전트를 실행할 수 있고, OpenAI 관리형 샌드박스뿐 아니라 자체 인프라와 파트너 샌드박스를 선택할 수 있습니다. 긴 세션을 위한 컨텍스트 압축, 필요한 도구 정의만 불러오는 도구 검색, 병렬 도구 호출, 하위 에이전트 조율을 제품 기능으로 제공합니다.

### 개발자에게 중요한 이유

지금까지 에이전트 제품의 상당 부분은 모델 호출보다 하네스 구현에 들어갔습니다. 세션 복구, 파일 보존, 도구 선택, 병렬 실행, 중간 산출물 관리가 대표적입니다. Agents API는 이 영역을 관리형 기반으로 이동시킵니다. 팀은 하네스를 직접 만드는 대신 자사 데이터, 도구, 승인 규칙과 사용자 경험에 집중할 수 있습니다.

### Lee’s Take

에이전트 실행 기반이 API가 되면 “모델을 붙였다”는 사실은 더 빨리 평준화됩니다. 차별점은 어떤 작업을 맡기고, 어떤 증거를 남기며, 어떤 조건에서 사람에게 판단을 돌려주느냐입니다. L-Proof-AI가 초안을 자동으로 만들되 승인 없이는 발송하지 않는 이유와 같은 맥락입니다.

### 이번 주 할 일

- 반복 업무 하나를 골라 `입력 → 에이전트 작업 → 사람이 승인 → 외부 반영` 경계를 문서로 그려봅니다.
- 장기 실행 실패 시 재시작 기준과 중간 산출물 보존 위치를 먼저 정합니다.
- 관리형 샌드박스와 자체 실행 환경을 보안·비용·관측 가능성 기준으로 비교합니다.

**원문** [OpenAI — Introducing the Agents API](https://openai.com/index/introducing-the-agents-api/)

## 2. Cursor Projects, 수개월짜리 작업과 반복 실행을 하나의 프로젝트로

**발표일** 2026-09-10
**검증 등급** 03 · 공식 확인
**직접 테스트** 아직 하지 않음

### 사실 요약

Cursor가 장기간 유지되는 컨텍스트와 조정 에이전트를 중심으로 한 Projects를 베타로 공개했습니다. 조정 에이전트는 직접 코드를 쓰기보다 작업을 계획하고 하위 에이전트에 위임한 뒤 결과를 사람에게 가져옵니다. 프로젝트는 클라우드 환경에서 계속 실행되며, 여러 실행 환경에 걸쳐 공유되는 파일과 작업 지식을 유지합니다. Slack 채널 감시, 예약 실행, PR 추적 같은 반복 작업도 프로젝트에 연결할 수 있습니다.

### 개발자에게 중요한 이유

에이전트 사용의 병목이 프롬프트 작성에서 컨텍스트 운영으로 이동하고 있습니다. 같은 저장소를 다루더라도 매번 설정과 테스트 방법을 다시 가르치면 장기 업무가 되지 못합니다. 공유 컨텍스트와 반복 실행이 결합되면 에이전트는 일회성 도구가 아니라 팀의 운영 프로세스에 가까워집니다.

### Lee’s Take

“오래 기억하는 에이전트”에는 오래 남는 실수도 함께 생깁니다. 어떤 지식을 공유 컨텍스트에 남길지, 누가 수정할지, 언제 폐기할지를 정하지 않으면 낡은 규칙이 자동으로 복제됩니다. 메모리 기능보다 메모리의 검토 절차가 먼저입니다.

### 이번 주 할 일

- 저장소의 설치·테스트·배포 절차를 에이전트가 재사용할 수 있는 짧은 문서로 만듭니다.
- 장기 프로젝트 메모리에서 자동 저장할 정보와 사람 확인 후 저장할 정보를 구분합니다.
- 예약 작업은 외부 반영 전에 반드시 검토 상태를 통과하도록 설계합니다.

**원문** [Cursor — Projects](https://cursor.com/changelog)

## 3. GitHub Copilot 코드리뷰, 셸 검증과 다중 에이전트 분석 확대

**발표일** 2026-09-11
**검증 등급** 03 · 공식 확인
**직접 테스트** 아직 하지 않음

### 사실 요약

GitHub는 Copilot 코드리뷰가 수정된 지적 사항을 재검토 때 자동으로 해결 처리하고, 자동 수정 제안에 변경 내용을 반영한 커밋 메시지를 생성한다고 발표했습니다. 리뷰 에이전트는 파일 읽기를 넘어 빌드·테스트·대상 스크립트 실행 등에 셸 도구를 사용합니다. Lite 리뷰에도 여러 에이전트의 분석을 합치는 방식이 적용됐습니다.

GitHub가 공개한 내부 실험에서는 다중 에이전트 방식이 실제로 반영된 리뷰 의견 수를 심각도별로 높였고, 비용은 감소했다고 설명합니다. 이 수치는 GitHub의 자체 실험 결과이며 독립 검증 수치는 아닙니다.

### 개발자에게 중요한 이유

코드리뷰 AI가 diff를 읽고 문장을 생성하는 단계를 넘어, 실행 결과를 근거로 판단하는 쪽으로 이동하고 있습니다. 리뷰 품질은 모델의 추론만이 아니라 어떤 명령을 허용하고, 어떤 테스트 결과를 증거로 채택하며, 실패를 어떻게 표시하는지에 따라 달라집니다.

### Lee’s Take

자동 해결 처리는 편하지만 “스레드가 닫혔다”와 “문제가 해결됐다”는 같은 말이 아닙니다. 고위험 변경에서는 사람이 테스트 결과와 변경 의도를 함께 확인해야 합니다. AI 리뷰가 강해질수록 승인자는 문법보다 시스템 영향과 배포 위험에 집중해야 합니다.

### 이번 주 할 일

- AI 리뷰 의견에 빌드·테스트 실행 근거가 포함되는지 확인합니다.
- 인증·결제·데이터 삭제처럼 고위험 경로는 자동 해결 대상에서 제외합니다.
- 자동 생성된 커밋 메시지가 실제 변경 의도를 설명하는지 리뷰 규칙에 넣습니다.

**원문** [GitHub — Auto-resolution and analysis updates in Copilot code review](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/)
