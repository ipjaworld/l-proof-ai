# AI가 먼저 말을 걸 때

고객과의 통화가 비행기 출발 직전에 잡혀 있었습니다. 사용자가 일정을 봐달라고 하기 전에 AI가 빠듯한 일정을 발견하고, 통화 시간을 옮길지 물었습니다. Anthropic이 Claude Duet을 소개하며 전한 초기 사용자의 사례입니다. 독립적인 성능 평가라기보다, 이 제품이 어떤 일을 맡으려는지 보여주는 장면입니다. [Claude Duet 소개](https://claude.com/resources/articles/claude-duet)

질문에 답하는 AI라면 답이 맞는지 읽어볼 수 있습니다. 먼저 알려주는 AI에게는 다른 궁금증이 생깁니다. 알려준 일은 눈에 보이는데, 중요하지 않다고 판단해 넘긴 일은 어떻게 확인할까요.

이번 11호에는 먼저 일을 찾는 에이전트와 함께, 여러 에이전트를 다시 하나로 합치는 설계 사례, 새 Kimi 모델, 실행 환경과 권한·사용 지표의 변화도 담았습니다. 10월 20~25일 자료를 살피고 기존 호에서 다룬 발표는 제외했습니다. 아래 소식은 **03 · 공식 확인**입니다. 발표 주체의 자료와 문서를 확인한 수준이며, 제품 동작과 성능을 직접 재현한 결과는 아닙니다. 마지막 ‘L-Proof의 해석’은 이 자료를 바탕으로 한 별도의 판단입니다.

## Claude Duet — 부탁하기 전에 일을 찾아오는 AI

Anthropic은 10월 21일 Claude Duet의 연구 프리뷰를 열었습니다. 미국의 Pro·Max 구독자부터 대기 명단으로 받으며, iOS·Android 별도 앱과 웹에서 제공합니다. 기존 Claude 요금제의 사용 한도를 함께 씁니다.

Duet은 연결된 앱을 살피고 아침 브리핑을 보내거나, 주의가 필요한 일을 먼저 알려줍니다. 자체 브라우저가 있는 가상 머신에서 작업하므로 사용자의 노트북을 켜둘 필요는 없습니다. 다만 **연결 계정을 몇 시간마다 확인하며, 그 점검도 사용 한도를 소모합니다.** 하루 종일 일한다는 설명을 실시간으로 모든 변화를 감시한다는 뜻으로 읽으면 안 됩니다. 아직 사용자가 Duet의 브라우저를 직접 볼 수도 없습니다. [이용 범위와 작동 방식](https://claude.com/resources/articles/claude-duet)

23일 공개된 안전 설명은 중요한 행동을 실행하기 전에 목적지·내용·수신자를 보여주고 승인을 기다리는 절차를 다룹니다. 작업 모델과 별도로 행동이 사용자 의도에 맞는지 확인하고, 보낼 메시지의 민감정보도 검사한다는 설명입니다. Anthropic 스스로도 승인 요청이 너무 잦으면 사람이 제대로 읽지 않고 넘길 수 있다고 적었습니다. 무엇을 알려줄지뿐 아니라, 언제 사람을 멈춰 세울지도 아직 조정 중인 제품입니다. [안전·개인정보 보호 설명](https://claude.com/resources/articles/claude-duet-safety-privacy-and-security)

## Anthropic — 팀마다 만든 에이전트를 다시 합쳐본다면

회사에 담당 부서가 많다고 AI도 부서 수만큼 필요할까요. Anthropic이 10월 22일 공개한 설계 가이드는 조직마다 만든 전문 에이전트를 조정하는 과정에서 문맥이 빠지고, 응답이 느려지는 사례를 짚었습니다. 여러 기업 적용 사례에서 필요한 스킬과 도구를 그때그때 불러오는 단일 에이전트가 더 나은 결과를 낸 경우가 있었다는 보고입니다. 모든 업무에 통하는 비교 실험으로 발표한 것은 아닙니다.

여기서 하나로 합친다는 말은 모든 규칙을 긴 프롬프트에 몰아넣는다는 뜻이 아닙니다. 스킬과 도구의 짧은 설명을 먼저 보여주고, 필요한 내용만 불러옵니다. 대화와 작업 결과는 같은 에이전트가 이어받습니다. 반면 독립적인 병렬 조사나 검증, 권한 분리가 필요한 작업에는 여전히 서브에이전트를 쓸 이유가 있습니다. [설계 가이드](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

가이드에는 합친 뒤 나빠진 사례도 나옵니다. 고객상담용 샘플 에이전트의 지연은 줄었지만, 주문 조회 도구를 가진 주 에이전트가 배송 담당에게 날짜를 묻지 않고 답해버렸습니다. 이 실패는 두 번 실행한 가운데 한 번에만 나타났습니다. 구조를 줄였다는 사실보다, 그 과정에서 어떤 확인 절차가 사라졌는지가 구체적으로 드러납니다. 함께 공개한 전환 키트도 기존 구조를 먼저 살펴보고, 합칠 것과 남길 것을 나눠 검토하도록 구성돼 있습니다. [공식 전환 키트](https://github.com/anthropics/single-agent-loop-kit)

## Kimi K3.1 Pro — API로 쓰는 날과 내려받는 날은 다르다

Moonshot의 새 모델 Kimi K3.1 Pro는 100만 토큰 문맥을 지원하며, Kimi 앱·Work·Code와 API에서 사용할 수 있습니다. Vercel도 10월 23일 AI Gateway 제공을 발표했습니다. 함께 나온 Highspeed는 같은 모델 능력으로 약 2~3배 빠르게 응답한다는 개발사 설명입니다. 직접 측정한 속도는 아닙니다. [Kimi 공식 소개](https://www.kimi.ai/blog/kimi-k3-1-pro) · [Gateway 제공 발표](https://vercel.com/changelog/kimi-k3-1-pro-and-kimi-k3-1-pro-highspeed-are-available-now-in-ai-gateway)

이번에는 코딩뿐 아니라 3D 작업도 전면에 나왔습니다. 공식 자료는 Blender·CAD용 코드를 작성하고 실행해 형상과 재질을 고치는 방식을 소개합니다. 웹과 앱의 3D Make에서는 결과물을 미리 보고 편집할 수 있습니다. 완성된 모습을 보는 데서 그치지 않고, 물체의 구조를 다시 수정하는 작업까지 염두에 둔 구성입니다.

성능 숫자는 범위를 나눠 읽을 필요가 있습니다. Moonshot의 내부 장기 코딩 평가에서는 K3의 55.95%에서 K3.1 Pro의 61.2%로 올랐습니다. 여러 단계의 실행과 도구 사용을 보는 자체 평가이므로, 일반 개발 작업의 성공률로 옮겨 쓸 수는 없습니다. **전체 가중치 공개는 11월 4일까지로 예고돼 있습니다.** 지금 API로 시험하는 것과 자체 인프라에 내려받아 운영하는 것은 아직 같은 선택지가 아닙니다. [평가와 가중치 공개 안내](https://www.kimi.ai/blog/kimi-k3-1-pro)

## Google — AI가 기다리는 동안 컴퓨터도 쉬게 한다

에이전트는 코드를 실행하다가 모델의 다음 판단을 기다리고, 다시 브라우저를 움직이다가 사람의 답을 기다립니다. 실행 환경을 계속 켜두면 기다리는 시간에도 자원이 묶입니다. 매번 종료하면 작업하던 상태를 되살려야 합니다.

Google이 10월 22일 발표한 Agent Compute Engine은 이런 반복에 맞춘 실행 환경입니다. 에이전트마다 하드웨어로 격리된 작은 가상 머신인 microVM을 주고, 쉬는 동안 상태를 저장했다가 빠르게 재개하는 구조를 설명합니다. 작업 파일과 문맥을 유지할 저장 공간도 붙입니다. 이미 Gemini 에이전트를 지원하는 데 쓰고 있지만, **고객용 프리뷰는 향후 수개월 내 제공 예정**입니다. 지금 누구나 사용할 수 있는 서비스로 발표된 것은 아닙니다. [공식 발표](https://cloud.google.com/blog/topics/ai-infrastructure/introducing-agent-compute-engine-and-expanded-agent-governance)

실행 공간과 인증정보를 나눈 점도 볼 만합니다. Google은 샌드박스 안에 서비스 자격증명을 두지 않고, 외부로 나가는 요청에 필요한 인증정보를 붙이는 방식을 설명합니다. 에이전트가 실행하는 코드에서 비밀 키를 직접 읽을 수 없도록 하려는 설계입니다. 다만 키가 보이지 않는 것과 허용된 서비스에서 잘못된 행동을 하지 않는 것은 별개의 문제입니다. 격리된 컴퓨터를 줘도 어떤 요청을 통과시킬지는 남습니다. [microVM과 인증 구조](https://cloud.google.com/blog/topics/ai-infrastructure/agent-compute-engine-deep-dive)

## GitHub — ‘기타’에 묻혀 있던 도구에 이름이 붙었다

팀이 만든 스킬과 MCP 서버를 배포했는데 사용 보고서에는 전부 ‘기타’로 묶인다면, 무엇이 쓰이고 있는지 알기 어렵습니다. GitHub는 10월 22일 Copilot 사용량 API에 사내 스킬·커스텀 에이전트·MCP 서버 등의 설정된 이름을 표시하기 시작했습니다. 항목별 목록도 레코드당 최대 5개에서 25개로 늘리고, 나머지를 ‘기타’로 합칩니다. 과거 날짜의 보고서까지 이름이 복원되지는 않습니다. [변경 기록](https://github.blog/changelog/2026-10-22-custom-skills-agents-and-mcp-servers-in-usage-metrics-api/)

숫자에 붙은 이름만큼, 무엇을 세는지도 중요합니다. 공식 문서에서 스킬의 상호작용 수는 호출 횟수이고, 커스텀 에이전트는 시작 횟수입니다. **MCP는 성공·실패를 포함한 연결 및 재연결 시도 횟수**입니다. 이미 연결된 서버에서 도구를 호출해도 이 수치는 늘지 않습니다. 자주 재연결되는 서버가 안정적으로 일하는 서버보다 활발해 보일 수 있는 셈입니다. [지표별 집계 정의](https://docs.github.com/en/enterprise-cloud%40latest/copilot/reference/copilot-usage-metrics/copilot-usage-metrics)

이름 보고는 지원 클라이언트와 버전에 따라 달라집니다. IDE의 기본 채팅 텔레메트리에서는 이름을 보고하지 않으며, 오래된 클라이언트나 텔레메트리 차단 때문에 사용량이 적게 잡힐 수 있습니다. 조회 권한과 사용 지표 정책 설정도 필요합니다. 팀 내부 도구가 얼마나 채택됐는지 살필 자료가 늘어난 것이지, 이 숫자만으로 도구의 성과나 전체 사용 내역을 확정할 수 있게 된 것은 아닙니다.

## Vercel — 매출을 읽는 AI에게 고객 수정 권한까지 줄 필요는 없다

Vercel Connect는 10월 23일 Stripe용 관리형 API 키를 추가했습니다. 에이전트나 작업별로 권한을 제한한 키를 만들고 보관하는 기능입니다. 일일 매출 보고에는 결제 내역을 읽는 권한만, 고객 등록 업무에는 고객 정보를 쓰는 권한을 주는 식으로 나눌 수 있습니다. 기존 MCP 연결과 직접 API 키를 가져오는 방식도 유지됩니다. [공식 발표](https://vercel.com/changelog/vercel-connect-adds-managed-stripe-api-keys)

설정에서 권한을 고르면 Vercel이 Stripe 계정에 키를 만들기 때문에 개발자가 비밀 키를 복사해 붙일 필요가 없습니다. 재배포 없이 교체할 수도 있지만, 전환 중 기존 키는 최대 24시간 유효합니다. 키 교체와 즉시 접근 차단을 같은 동작으로 생각하면 안 되는 부분입니다.

이 기능을 쓰더라도 보고서를 만드는 AI와 고객을 등록하는 AI의 권한을 똑같이 설정하면 둘을 나눈 효과는 줄어듭니다. 작업별 키를 쉽게 관리할 수 있게 된 만큼, 실제 업무에 필요한 읽기·쓰기 범위를 정하는 일이 더 구체적으로 남습니다.

## L-Proof의 해석

### AI가 알리지 않은 일도 평가할 수 있을까

Duet이 먼저 알려주는 일은 사용자가 확인하고 고칠 수 있습니다. 반면 알림에서 빠진 메일은, 사용자가 브리핑만 읽어서는 무엇이 빠졌는지 알기 어렵습니다. L-Proof는 이런 제품에서 답변의 정확도만큼 **알리지 않기로 한 판단을 나중에 살펴볼 수 있는지**가 중요해질 것으로 봅니다.

가령 거래처의 짧은 메일에 다음 주 납기 변경이 적혀 있다고 해봅시다. AI가 흔한 일정 안내로 분류해 아침 브리핑에서 뺐다면, 사용자는 브리핑에 실린 내용만 검토해서는 그 누락을 찾기 어렵습니다. 실제 Duet에서 관찰한 사고가 아니라, 먼저 정보를 골라주는 제품을 평가할 때 생각해볼 상황입니다.

그렇다고 모든 메일의 분류 이유를 읽게 하면 AI에게 맡긴 일이 다시 사람에게 돌아옵니다. 매일 전부 확인하기보다는, 특정 거래처나 마감 관련 항목 가운데 무엇을 제외했는지 가끔 표본으로 살펴볼 수 있다면 어떨까요. 알림을 줄이는 설정과 놓친 일을 찾는 기능은 서로 다른 역할을 할 수 있습니다. 이런 확인 방법이 제품에 있는지, 실제로 도움이 되는지는 별도로 검증해야 합니다.

L-Proof가 보고 싶은 것은 알림을 얼마나 적게 보냈다는 숫자만은 아닙니다. 사람을 덜 방해하면서도 중요한 일을 놓치지 않았는지, 놓쳤다면 그 판단을 다음번에 어떻게 바꿀 수 있는지입니다.

### 에이전트를 합쳐도 남겨야 할 확인

Anthropic의 단일 에이전트 가이드는 ‘많이 나눌수록 잘한다’는 기대를 돌아보게 합니다. 하지만 배송 날짜를 묻지 않고 답한 사례는 반대쪽도 보여줍니다. 작업을 넘기는 단계를 없앴더니, 그 단계에서 하던 확인까지 빠질 수 있습니다.

L-Proof는 에이전트를 합칠 때 속도와 최종 답변을 비교하는 데서 한 걸음 더 나갈 필요가 있다고 봅니다. 사라질 에이전트가 맡았던 일 가운데 무엇이 단순한 전달이었고, 무엇이 꼭 필요한 확인이었는지 나눠보는 것입니다. 배송 담당을 없애더라도 배송일을 확인해야 한다는 조건까지 없어지는 것은 아닙니다.

서로 떨어진 자료를 동시에 조사할 때는 나누는 편이 유리할 수 있습니다. 다만 같은 주문을 여러 담당이 반복해서 요약하고 있다면, 경계를 줄이는 실험을 해볼 이유가 있습니다.

에이전트를 합쳐 답이 더 빨리 돌아왔다면, 그 과정에서 무엇이 줄었는지도 살펴봐야 합니다. 불필요한 전달만 사라졌을까요. 아니면 꼭 확인해야 했던 일까지 함께 빠진 걸까요.
