## 1. 다음 작업자가 먼저 이해해야 할 것

이 작업의 핵심은 카피를 더 잘 쓰거나 카드 배치를 정돈하는 것이 아니다. **글을 읽기 전에, 스크롤에 따른 시각적 변화만으로 제작 과정을 알아볼 수 있어야 한다.** 이전 작업은 이 요구를 여러 차례 놓쳤다.

사용자의 핵심 피드백:

> “왜 사람이 글을 읽을거라고 생각하는거야?”
>
> “사실을 확인할 때 종이가 바뀌는 연출이 필요해.”
>
> “그 본문을 스크롤해서 밑으로 내려온 다음에 빈 공간에 글이 써지는 것처럼 표현”

일반 방문자는 ChatGPT를 알아도 Codex, Antigravity 같은 도구 이름은 모를 수 있다. 구현자가 익숙한 제품명을 방문자의 사전 지식으로 가정하지 않는다. 기술명 대신 **하는 일**을 보여준다. 이 원칙은 명칭뿐 아니라 화면 구성과 동작에도 적용한다.

현재 코드가 있다는 이유로 그 방향이 승인됐다고 간주하지 않는다. 빌드 성공, 화면 표시, 모바일 확인은 시각적 전달의 성공을 의미하지 않는다.

## 2. 사용자에게 확인된 방향

- 첫 화면은 정보 욕심을 줄인다. 긴 설명, 많은 카드, 여러 CTA를 한꺼번에 보여주지 않는다.
- 빈 종이가 자료와 내용을 얻고, 검토와 사람의 승인을 거쳐 이메일로 이어지는 흐름을 스크롤로 표현한다.
- 초기 논의의 1·2번, 3·4번은 각각 같은 화면에서 보여줘도 된다는 의견이 있었다. 현재 코드의 다섯 장면을 고정 요구사항으로 해석하지 않는다.
- COREVIS는 특히 제작 흐름 구간의 **연속적인 시선 이동과 스크롤 변화**를 참고한다. 브랜드·모델·화면을 복제하는 것이 목적은 아니다. Three.js 도입은 사용자 허용 범위다.
- 작성과 검토는 역할 이름으로 일반화한다.
  - **작성자 AI · 사실과 해석** — 사용자가 명시적으로 맞다고 확인했고 HTML 반영 완료.
  - **검수자 AI · 원고 검토** — 특정 서비스명 대신 일반화하라는 사용자 지시.
  - **이건하 · 최종 발행 승인** — 현재 표시. 사람의 최종 승인 역할을 유지한다.
- 검수자 AI의 스캔 판 아이디어 자체는 좋다는 피드백이 있었다. 다만 제목을 스캔하는 것처럼 보이거나, 설명을 읽어야 알아보는 결과는 의도와 다르다.
- 마지막 이메일 전달 장면은 접기 동작에 집착하지 않는다. 페이드여도 좋으니 시각적 완성도가 우선이다.
- 마지막 안내 CTA의 높이와 여백을 늘리고, 이메일 입력·구독 버튼은 더 아래 별도 영역으로 분리한다.
- 사용자가 직접 스크롤할 수 있는 로컬 서버를 유지한다. 이전에 확인이 안 된다는 불만이 있었다.

## 3. 반복하지 말아야 할 실패

| 이전 접근 | 사용자 반응 / 인계 시 주의 |
| --- | --- |
| 설명 카피와 카드로 차이를 전달 | 읽어야만 차이가 보인다. 정보 추가로 해결하지 않는다. |
| Three.js만 넣고 고정된 구도 유지 | COREVIS의 스크롤 감각이 아니다. 라이브러리 채택 자체를 성과로 삼지 않는다. |
| 종이를 봉투에 넣고 접어 날림 | 겹치는 면과 조잡한 형상이 드러났다. 해당 모델은 제거했다. |
| 본문을 확대하고 밑줄·말풍선을 추가 | 의도는 이해되지만 실제 연출에서 그렇게 느껴지지 않는다고 지적받았다. |
| 검수자만 일반화하고 작성자는 CODEX로 둠 | 일반 방문자 관점을 일관되게 적용하지 못했다. 현재는 수정했다. |
| 최종 정지 화면과 단계 버튼만 확인 | 중간 변화가 핵심이다. 시작→전환→빈 여백→작성 중 상태를 실제 스크롤로 확인해야 한다. |

특히 이전 답변의 “확인 완료”를 사용자 만족이나 디자인 승인으로 재해석하지 말 것. 마지막 v4 연출에 대한 만족 확인은 받지 않았다.

## 4. 현재 구현 상태 — v4

작업 대상: `design/rebuild-immersive/`.

운영 Next.js 홈페이지가 아닌 별도의 정적 HTML/Three.js 시안이다. 현재 흐름:

1. 빈 종이와 자료 조각.
2. 같은 종이에 실제 12호 제목·본문 발췌·해석 영역 표시.
3. 종이 내부 내용이 위로 스크롤되며 아래 빈 여백이 드러남. 스캔 판이 지나간 뒤 검토 예시 문장이 커서와 함께 순차 작성됨.
4. 사람의 승인 도장 연출.
5. 종이와 3D 배경이 사라지고 HTML 이메일 지면이 페이드로 나타남.
6. 큰 안내 CTA → 최근 발행물 두 개 → 별도 이메일 입력 영역 → 푸터.

v4의 구체적인 구현:

- `paintPaper()`가 CanvasTexture를 다시 그린다. 본문 영역에 클리핑을 적용하고 최대 650px 위로 이동시킨다. 상단 L-Proof 표시는 고정한다.
- 새 여백에는 “승인 ≠ 사람의 확인 / 자동으로 승인되는 경우와 / 사람에게 묻는 경우를 구분하기.”가 스크롤 진행률에 따라 써진다.
- `reviewProgress`가 검토 장면 안의 진행률이다. 스캔 후 작성으로 이어진다.
- v3의 떠 있는 HTML 말풍선은 삭제했다.
- 현재 검토 문장은 연출용 예시이며 실제 AI 교정 로그나 내부 사고 기록이 아니다.
- 구독 폼은 이메일 형식 입력을 체험하는 용도다. 실제 등록 요청·저장·발송은 하지 않는다. 제출 시 미전송 안내와 공식 구독 페이지 링크를 보여준다.

**남은 판단 / 점검:**

- 종이의 내부 스크롤과 새 글 작성이 설명 없이도 전달되는지 아직 사용자 승인 없음.
- 검토 예시의 글자가 작은 화면에서 다시 읽기 과제로 느껴지지 않는지 확인 필요.
- v4는 앞 본문을 위로 밀어내기 때문에 스캔 대상과 새로 쓰이는 문장의 관계가 충분히 보이는지 재평가 필요.
- 다음 승인 장면에서는 종이 내부 스크롤이 원위치로 돌아온다. 이 복귀가 자연스러운지, 검토 결과가 사라지는 것처럼 느껴지는지 확인 필요.
- 현재 다섯 장면, 도장, 카피 위치, 카메라 좌표는 구현 선택이지 승인된 설계가 아니다.
- CSS는 반복 보완으로 덮어쓰기 규칙이 누적되어 있다. 방향이 결정된 뒤 정리할 수 있으나 지금은 불필요한 리팩터링보다 전달 방식 판단이 우선이다.

## 8. 작업 경계와 다음 시작점

운영 배포·푸시·커밋은 하지 않았다. 인계 시 `git status`:

```text
 M content/editions/2026-10-29-thu.json
?? design/
?? docs/ISSUE_12_EXECUTION_HANDOFF.md
```

발행물 JSON과 ISSUE_12 인계 파일은 이번 디자인 작업 전부터 있던 사용자 변경이다. 덮어쓰거나 디자인과 묶어 커밋하지 않는다. 이 인계 파일과 README의 인계 링크는 위 조회 이후 추가했다.

새 담당자는 이 문서를 먼저 읽고 현재 시안을 실제로 스크롤한다. 사용자의 재개 요청을 받으면, 문구 미세 수정부터 반복하지 말고 **한 장면에서 무엇이 눈에 띄게 변하는지**를 기준으로 전환 설계를 먼저 판단한다. 정지 화면의 장식보다 변화 전후의 대비와 연결이 우선이다. 사용자에게 이미 정한 내용을 다시 묻거나 현재 결과를 승인된 것으로 전제하지 않는다.

프로젝트 AGENTS.md의 Next.js 로컬 문서 확인, Wiki 조회, 비밀정보 취급 등 지침을 따른다. 예약 자동화의 인증·API 운영 경로 개선은 별도 미완료 우선 과제다. 홈페이지 작업과 섞어 범위를 넓히지 않는다.
